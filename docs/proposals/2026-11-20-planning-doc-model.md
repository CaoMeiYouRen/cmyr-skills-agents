## 1 变更摘要

四个项目的规划文档（`todo` / `backlog` / `todo-archive` / `archive/`）已各自演进，但**粒度、进度可见性、归档载体**三处不一致，跨项目协作与机检都要逐项目适配。本提案只统一这三处的**模型**，不统一阶段编号体系与实现细节。

- 上游（本提案通过后新增）：`standards/planning-docs.md`（规则）+ `standards/templates/planning-docs.md`（项目填充模板）
- 项目侧：`todo.md` 进度表、大 / 小条目分层、归档命名与索引表、机检规则

三条原则：

1. **前向统一**：新阶段按 v1 执行；存量只做机械改名，不改正文。
2. **模型统一、参数自理**：阶段编号、ID 格式、窗口阈值由项目自定；唯一性由项目保证。
3. **不新增事实源**：不引入第四个文档载体；预规划另案。

## 3 建议改动

### 3.1 粒度模型

| 层 | 定义 | 必填字段 | 提交 | 审计 |
| :--- | :--- | :--- | :--- | :--- |
| 阶段 | 一次授权范围 | 目标 / 容量基线 / 执行顺序 / 不做范围 | — | — |
| 大条目 | 一个可独立验收的交付包 | 8 要素（目标 / 优先级 / 范围 / 验收 / 不做什么 / 依赖 / 交付物 / 风险） | 1-N 次 | 至少 1 轮 |
| 小条目 | 可独立提交的最小单元 | 目标 / 验收 / 交付物 / 依赖（其余继承大条目） | 1 次 | 跟随提交 |

- **阶段大条目**：默认 4-6，**上限 8**；用到第 7-8 项时必须在阶段头写「为何不拆成两个阶段」。8 是上限，不是目标值。
- **小条目数量**：每个大条目 1-5 个；单阶段总数 **≤ 20**，建议 10-15；超过 15 需说明为何不拆阶段。
- **提交与审计粒度**：小条目默认**独立提交、独立审计**；仅当强耦合（同一文件、同一契约变更、必须同一 commit 才可编译）时合并批次，并在条目内写明合并理由。
- **ID**：**建议** `<大条目ID>.<序号>`（如 `M63.1.3`），不要求跨项目一致；**必须**项目内唯一，且能在进度表「提交」列定位到实际提交。存量 ID 不改。
- **字段分层是硬要求**：小条目只写 4 项，不得复制大条目 8 要素，避免 `todo.md` 与归档分片体量翻倍。

### 3.2 进度表

`todo.md` 当前阶段标题下第一张表，固定 6 列，项目可自行增补列：

| 大条目 | 小条目 | 状态 | 提交 | 审计 | 容量（计划→实际） |
| :--- | :--- | :--- | :--- | :--- | :--- |
| M63.1 日志可消费化 | 3/4 | 进行中 | 4 | R1 Reject → R2 Pass | 6-8 → 4 commits |

- 行 = 大条目；`小条目` 列写「已闭环 / 总数」。
- `状态` 收敛为四值：`未开始` / `进行中` / `已闭环` / `已阻塞`。
- `容量` 默认单位 commits，项目可改为 files 或行数。
- 机检约束：表行数 = 正文大条目数；`已闭环` 行数 = 归档时 `[x]` 数量；状态值必须在四值内。

### 3.3 归档载体

| 项 | v1 约定 |
| :--- | :--- |
| 路径 | 主文件 `docs/plan/todo-archive.md`，分片目录 `docs/plan/archive/` |
| 主文件职责 | 索引表 + 近线窗口；阈值项目自定，模板默认 400 行 |
| 分片命名 | `todo-archive-phases-<起>[-<止>].md`、`roadmap-phases-<起>[-<止>].md`；区间必须连续 |
| 分片粒度 | todo 与 roadmap 分片分开，不得合并为同一文件 |
| 索引表 | 固定 4 列：阶段 / 主题 / 归档文件 / 归档日期；倒序、覆盖全部分片、无重复、无正文 |
| 归档块必填 | 阶段名与时间 / 大条目清单与状态 / 提交清单 / 质量门结果 / Review Gate 结论与轮次 / 未覆盖边界 |

存量改名清单：

| 项目 | 现状 | v1 动作 | 影响面 |
| :--- | :--- | :--- | :--- |
| dependfix | 48 个符合命名式；3 个补丁式（`m2-m55` / `m10-c53-c59c61` / `m6-m7-t711`） | 48 个不动；3 个保留原名，在 `archive/index.md` 标注「遗留命名，勿仿效」 | 0 处链接改动 |

| caomei-ui | 19 个 `phase-*.md` | 改名为 `todo-archive-phases-<起>[-<止>].md` | `todo-archive.md` 36 处、`roadmap.md` 19 处、`archive/index.md` 若干 |
| caomei-auth | `docs/archive/completed-work.md`（主题式） | 冻结为历史主题归档；下一阶段起新建阶段式归档与索引 | 新增文件，不改旧文件 |

改名约束（保真）：

- `git diff` 只允许出现两类内容：文件重命名、因路径变化产生的链接与锚点修正。
- 核验方式：剥离链接目标后的非空行多重集相等（沿用 momei `M61.2` 的保真口径）+ 项目链接门禁 exit 0。
- 不得借改名顺带改正文、调顺序或补字段。

### 3.4 机检

| 规则 | 判定 | 分档 |
| :--- | :--- | :--- |
| 进度表存在且行数一致 | 行数 = 正文大条目数，状态值合法 | dependfix / momei / caomei-ui 必须；caomei-auth 门禁就绪后必须 |
| 归档索引一致性 | 倒序、全覆盖、无重复、无正文、文件名匹配命名式 | dependfix 扩展 `check-doc-governance`；其余建议接入 |
| 归档块必填字段 | 6 项齐全 | warning，不阻断 |

规则以 `standards/templates/planning-docs.md` 提供默认实现说明，项目按现有门禁栈落地，不引入新工具链。

## 4 需要项目 agent 研判的问题

1. dependfix 的 3 个补丁式命名是否接受保留并标注（推荐接受，避免改名后名实不符）。
2. caomei-ui 新阶段起是否产出独立 `roadmap-phases-*.md`，还是继续复用 `todo-archive-phases-*.md`（推荐独立）。
3. 主窗口阈值统一还是项目自定（上游建议项目自定，模板给 400 默认）。
4. backlog 条目字段规范化是否纳入本期（dependfix 为 44,911 / 45,000 字符，需先扩容或拆分）。
5. 进度表 `容量` 列的默认单位（上游建议 commits）。

## 5 验收标准

- [ ] `todo.md` 当前阶段头部存在 6 列进度表（项目可增列），行数 = 正文大条目数。
- [ ] 每个小条目项目内唯一，且 `提交` 列能定位到实际提交。
- [ ] 使用第 7-8 个大条目时，阶段头存在「不拆阶段」理由。
- [ ] 新增归档分片名匹配 `todo-archive-phases-<起>[-<止>].md` 或 `roadmap-phases-<起>[-<止>].md`。
- [ ] 归档索引表倒序、覆盖全部分片、无正文、无重复；有机检的项目 exit 0，无机检的项目人工核对并记录。
- [ ] 归档块 6 项必填齐全。
- [ ] 改名批次 `git diff` 只含 rename 与链接 / 锚点行，剥离链接目标后非空行多重集相等。
- [ ] caomei-auth 下一阶段产出阶段式归档，`completed-work.md` 未被改写。
- [ ] 失败判据：进度表行数与正文不一致、索引缺分片、改名批次含正文改动，任一出现即判未达标。

## 6 回滚

- 规范与模板：revert 对应提交。
- 改名批次：`git mv` 反向 + 链接反向重指，以改名前的 commit 为基线复核链接门禁。
- 已按 v1 产出且已归档的阶段不回改，只改规范与后续阶段。

## 7 本项目不做什么

- 不统一阶段编号体系（`M63` / `第八十阶段` / `Phase 38` 保持原样）。
- 不统一 ID 格式，只要求项目内唯一。
- 不重写任何项目的存量归档正文。
- 不改 `.github/workflows/todo.yml`（`todo-workflow` 能力不变）。
- 不包含「预规划阶段」，另案处理。
- 不替项目决定 backlog 拆分方案。
