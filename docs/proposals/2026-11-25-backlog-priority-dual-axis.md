## 1 变更摘要

给每个 backlog 候选两个 **1–5** 的整数评分——**重要度**与**紧急度**（数字越大越优先），并按四象限给出推进建议（首排 / 排期 / 快速评估 / 延后），取代单一优先级标签（`P0–P3`、`P2 · 长期`、`低优先级` 或完全没有字段）。

- 上游：**不新增独立 standards 文件**，评分口径写在提案内，由项目并入自己的 `docs/standards/planning.md`。理由：`standards/planning-docs.md` 仍处于提案阶段（[规划文档模型 v1](./2026-11-20-planning-doc-model.md)），现在再建一个规划标准会违反 [standards/README §1](../standards/README.md) 的「一条规则只写一次」。
- 项目侧：`docs/plan/backlog.md` 候选表加列 + 规划规范加一个小节；机检默认不加。
- 参考实现：caomei-ui 已落地（37 条候选，首排 1 / 排期 6 / 快速评估 0 / 延后 30，2026-11-25 快照）。本提案复用其锚点与象限，不重新发明一套。

三条原则：

1. **两轴分开打分**：重要度回答「不做会不会造成实质损失」，紧急度回答「现在不做会不会错过窗口或继续产生成本」。两者不合并成单一分数，也不互相折算。
2. **象限只排序、不授权**：与现有「不自动升级」规则一致。象限不构成进入 `todo.md` 的授权，唯一例外仍是插队清单。
3. **分数必须可复算**：每个分数在说明列给出证据、触发条件或时间窗，并标快照日期；不接受「感觉重要」。

## 3 建议改动

### 3.1 评分锚点（默认值，项目可覆盖）

| 分数 | 重要度：不做会不会造成实质损失 | 紧急度：现在不做会不会错过窗口 / 继续产生成本 |
| :-: | :--- | :--- |
| 5 | 安全 / 数据正确性 / 阻断下游构建发布 / 已确认功能缺陷 | 安全告警、已确认回归、发布阻断 |
| 4 | 有真实下游证据的能力或体验缺口，或用户明确指定的当前阶段方向 | 有明确时间窗（含发布窗口） |
| 3 | 质量或一致性收益明确，但有替代路径 | 下游正在等待，或 workaround 已产生成本 |
| 2 | 已有等价替代 | 条件触发接近命中，或按节奏推进且无硬时点 |
| 1 | 可选增强 | 无时间压力 |

补充口径（沿用 caomei-ui 裁定）：

- **方向分不等于点名最高**：用户给出方向（如「快速开发期以新组件为主」）时，按字面覆盖整组，同取 4 / 2；不得在组内挑少数条抬分。组内先后由用户在阶段登记时选择。
- **安全项**：可当期处置的已确认告警 → 5 / 5，抢占排期；受上游阻塞、当期无可行修复 → 5 / 3，写阻塞点与解禁触发。
- **分数是当期判断**：证据、时间窗或安全状态变化时同批更新；阶段登记前与每季度各复核一次。
- **示例**：发布收口 = 重要 5（阻断发布）/ 紧急 4（有明确窗口）→ 首排；受上游阻塞的依赖安全项 = 5 / 3 → 排期。

### 3.2 象限与动作

| 重要 | 紧急 | 建议 | 动作 |
| :-: | :-: | :--- | :--- |
| ≥4 | ≥4 | **首排** | 下一个可执行窗口优先；仍需用户授权启动 |
| ≥4 | ≤3 | **排期** | 按节奏逐步推进，不插队 |
| ≤3 | ≥4 | **快速评估** | 一轮取证内决定去留；不做则当场写入 `backlog.md` 的结论留档，不悬置 |
| ≤3 | ≤3 | **延后** | 保留候选与触发条件 |

- 象限只决定候选的**推进顺序与建议**，不构成进入 `todo.md` 的授权。
- 「快速评估」必须有结论落点：采纳、延后（写触发条件）或否决（写理由），三者之一。
- 同分 tie-break 由项目声明**可判定**规则（如「同等分数下新功能优先」）；禁止「按重要性排序」「按使用频率」这类不可复算表述。

### 3.3 载体与字段

| 项 | 约定 |
| :--- | :--- |
| 候选表 | 固定「重要 / 紧急 / 建议」三列；来源、说明列保留 |
| 说明列 | 至少给一项可复算依据：证据链接、触发条件、时间窗、快照日期 |
| 单一事实源 | 锚点与象限写在项目规划规范的一个小节；`backlog.md` 只落分数，不复述锚点 |
| 阶段登记 | 把该候选的分数写入登记记录的排序留痕；`todo.md` 不复制双轴分数 |
| 复评 | 阶段登记前、每季度、证据变化时更新；历史登记记录不回改 |

### 3.4 与既有标签的关系

| 既有形态 | 建议处置 |
| :--- | :--- |
| dependfix `P0–P3`（阶段条目 8 要素） | 保留为阶段内交付优先级，**不与双轴自动换算**；若要换算，项目自行定义并在规范写死。backlog 候选改用双轴 |
| momei 4 维矩阵（V / A / D / R） | 保留为**准入判断**；双轴用于**候选池排序**。同一候选可同时有矩阵结论与双轴分数，但不得互相替代 |
| `P2 · 长期`、`低优先级` 等正文标签 | 改为双轴 + 建议；正文可保留来源说明，但不得再承载排序职责 |
| 无优先级字段的候选 | 首次登记时必填双轴；存量可在下次触碰时补，不要求一次性全量重排 |

### 3.5 机检与审计

- 默认**不新增脚本守卫**：分数是自然语言判断，机检误报高。由 Review Gate 抽查「分数与说明依据是否相符、建议是否与象限规则一致」。
- 可选机检（项目已有 backlog 解析脚本时）：每个候选行有 1–5 整数两列、建议 ∈ 四值、建议与分数符合象限规则。分档：**建议**，不阻断。
- 审计口径：出现「象限 = 启动授权」或同一候选两套未分工的优先级口径，按 Review Gate 必查项处理。

## 4 需要项目 agent 研判的问题

1. **dependfix**：`P0–P3` 与双轴是否做换算？建议不换算——`P0` 含「安全阻断」语义，与紧急度的「时间窗」语义不同，硬映射会丢信息。
2. **momei**：4 维矩阵与双轴并存还是替换？建议并存并写死分工（准入 vs 排序）；若替换，需说明 `Value` / `Alignment` 的信息落到哪一轴、原阈值 1.5 / 1.0 是否废止。
3. **caomei-auth**：是否把「优先级」从阶段 8 要素中移出、只留双轴？还是两者都保留并在规范写分工？
4. **存量补分范围**：dependfix 147 条是「新登记必填、存量下次触碰时补」，还是设一个批次上限（如每阶段补 20 条）？本提案建议前者，避免一次性大改。
5. **快速评估的取证责任**：谁执行「一轮取证」、结论写在哪一节（建议 `backlog.md` 的结论留档节）？
6. **阶段取向与 tie-break** 写在哪：建议 `docs/standards/planning.md` 单点声明，避免 `AGENTS.md` 与规划规范双写。

## 5 验收标准

- [ ] 项目规划规范存在评分小节，含两轴锚点、象限规则、复评触发。
- [ ] `backlog.md` 候选池内的每个候选行有「重要 / 紧急」两个 1–5 整数与「建议」列。
- [ ] 每条候选的说明列至少有一项可复算依据（证据 / 触发条件 / 时间窗 / 快照日期）。
- [ ] 抽查 10 条候选，「建议」与象限规则零不符。
- [ ] 阶段登记记录保留候选的分数（排序留痕），`todo.md` 不复制分数。
- [ ] 规范中未出现「象限 = 启动授权」的表述；插队清单仍独立生效。
- [ ] 同一候选不存在两套未分工的优先级口径（旧标签已删除，或已写明分工）。
- 失败判据：任一候选缺分数、建议与象限不符、出现两套未分工口径，任一出现即判未达标。

## 7 本项目不做什么

- 不统一各项目的阶段编号、阶段取向与 tie-break 规则。
- 不规定分数由谁打，不把象限变成自动排期或自动启动。
- 不新增独立 standards 文件，不改 `capabilities/registry.json`。
- 不改插队例外清单，不改变「不自动升级」规则。
- 不要求存量候选一次性全量补分。
- 不替项目决定 4 维矩阵的去留。
