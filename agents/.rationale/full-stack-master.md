# Full Stack Master（agent）— 设计理由（Why）

> 面向维护者。执行编排角色时不需要读本文件；只有重构、合并、降级或删除该 agent 时才需要。
> 角色边界看 [../full-stack-master.agent.md](../full-stack-master.agent.md)，完整流程看 `full-stack-master` skill。

## 1. 存在理由

- 为端到端复杂任务提供**稳定的总控身份**：谁来拆阶段、谁来分派、谁保证质量门不被跳过。
- 把"多技能协作"从临时口头编排变成一个有边界、有交接关系的常驻角色。
- 没有它时的可观察损失：跨前后端任务缺少统一节奏，质量门与审查容易被跳过或重复劳动。

## 2. 设计哲学

第一性原理：**总控的价值是维持阶段秩序，而不是亲自执行所有阶段。**

由此派生：

- 只做编排与接棒，不变成万能执行器。
- 完整流程下沉到 skill，agent 只保留角色定位与交接边界。
- 同一时点只保留一个实现主责，避免多角色重做。

## 3. 关键假设

- 存在成体系的专业 agent（product-manager、system-architect、frontend/backend-developer、code-reviewer 等）与原子 skill。
- 存在可执行的质量门与审查机制。
- 调用方接受"先规划、后实现、再审计"的节奏。

专业 agent 或 skill 被改名/合并/删除时，角色矩阵与交接顺序必须同步重算，否则出现空转或断链。

## 4. 失效场景与删除判据

当以下条件**同时**成立时，本 agent 应降级为默认助手的一个模式或直接删除：

1. 编排已由平台/自动化（CI + hooks + 分支保护）固化，不再需要常驻角色维持秩序。
2. 专业 agent 数量收敛，路由逻辑简单到不需要独立总控。
3. 角色文件不再承载不可替代的交接边界信息。

降级/删除前必须确认：质量门、审查强制、提交边界与跨角色接棒都有替代载体。

## 5. 能力替代 vs 不可推断

- **能力替代型**：通用"先规划再实现、不要跳步骤"的提醒。
- **不可推断型**：专业角色矩阵、阶段到角色的路由、审计强制约定、与各 agent 的交接边界、任务粒度阈值（默认 10 文件 / 800 行）、Session 协议接入点。

## 6. 项目覆盖锚点

| 参数 | 默认值 | 项目覆盖位置 |
| :--- | :--- | :--- |
| 任务粒度阈值 | 10 文件 / 800 行新增 | 项目 `AGENTS.md` |
| 专业角色矩阵 | 见本 agent 文件 | 项目 `AGENTS.md`（新增/移除 agent 时同步） |
| 审计调用协议 | 见 `code-reviewer` 约定 | 项目 `AGENTS.md` 或 `docs/standards/*` |
| Session 状态目录 | `.session/` | 项目 `AGENTS.md` |

优先级：**技能/agent 默认 < 项目覆盖 < 会话覆盖**。

## 7. 关键取舍

- 用阶段秩序换取低返工，代价是流程开销，不适合一次性小改动。
- 通用性与可跨项目复用优先，项目特化规则一律下沉到项目 `AGENTS.md` / `docs/standards/*`，不在 agent 内硬编码。
