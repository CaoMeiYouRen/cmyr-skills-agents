# 多提交交付：拆分、顺序与冲突

单次提交用不上本文件；一次交付包含多个逻辑变更时，先按这里拆分再写消息。

## 1 划分批次

- 按功能 / 测试 / 文档 / 配置拆成独立提交单元；格式化、重命名单独成一次，不与功能混在一起。
- 先区分「用户已有改动」与「本次任务改动」，只暂存后者。
- **粒度**：硬阈值以 `code-reviewer` 为唯一权威（默认值见该技能），本文件不重述；经验值是 ≤5 文件 / ≤350 行，便于审查聚焦与单测定位。
- **例外**：单文件生成产物（如生成的 `.d.ts`）与纯新增文件（如新测试文件）超阈值不强制拆，但要在交付说明里写明「超出阈值但属单文件生成产物 / 纯新增」。

## 2 依赖顺序

- 每个 commit 必须能独立通过验证；不允许「后一个 commit 依赖前一个未提交的改动」。
- 被依赖的基础设施（类型、helper、字典、迁移）放前置 commit，引用方与测试放后面。
- 顺序要能解释：后续要 cherry-pick 或回滚时，按顺序挑不会打架。

## 3 锁文件冲突

**不要在 `pnpm-lock.yaml` 有冲突时 `git pull --rebase`**——rebase 会逐提交重放冲突，几乎必然失败，手动解 lockfile 的成本远高于重新生成。

远程有新提交时用三步替代：

```bash
git fetch origin
git reset --soft origin/master    # 改动保留在暂存区
pnpm install --no-frozen-lockfile # 重新生成干净的锁文件
git add -A && git commit
```

这只适用于锁文件冲突场景；普通代码冲突仍按正常 rebase/merge 处理，不要用 `reset --soft` 掩盖。

**不要手动编辑 `pnpm-lock.yaml` 解冲突**：手改锁文件会破坏完整性校验，得到一个「能装但不可信」的锁文件；宁可重新生成再对比差异。

## 4 变更记录（需要时）

- changelog / release note 按提交批次汇总，不按文件罗列。
- 说明哪些改动适合单独提交（可独立回滚），哪些适合压缩（同一次重构的中间态）。

## 5 检查清单

- [ ] 每个提交按功能边界拆分，未混入格式化与重命名。
- [ ] 每个提交可独立验证，依赖顺序已说明。
- [ ] 超出硬阈值的已拆分，或已声明单文件生成产物例外。
- [ ] 已识别无关改动与潜在冲突点。
- [ ] 锁文件冲突按第 3 节处理，没有使用 `git pull --rebase`。
