# Code Reviewer — 设计理由（Why）

> 面向维护者。调用本技能时不需要读本文件；只有重构、合并、降级或删除时才需要。
> 触发看 `SKILL.md` 的 `description`，工作流看 `SKILL.md` 正文；本文件只回答"为什么存在、何时该消失"。

## 1. 存在理由

- 把"这次改动能不能合并"从主观印象变成**有证据的 Gate 结论**，替代"看起来不错""代码能跑"这类无依据放行。
- 替代两种常见失败：作者自我审查（缺独立性）与无强度审查（只跑 lint 就给 Pass）。
- 没有它时的可观察损失：漏检的 correctness / 安全问题在合并后才暴露，返工成本远高于审查成本。

## 2. 设计哲学

第一性原理：**审查结论必须与证据强度匹配，没有最低验证证据不得放行。**

由此派生的核心设计：

- Gate 结论（Pass / Reject）与问题分级（blocker / warning / suggest）分离，不互相替代。
- 审查投入与改动风险匹配（audit-depth），不一视同仁。
- 复审只审修复点，避免无限深挖与上下文浪费。
- 默认只输出 review，不直接改代码——审查与实现是两种职责。

## 3. 关键假设

- 存在可读取的 diff 或明确的审查范围。
- 项目有可执行的 lint / typecheck / 测试等验证手段。
- 调用方愿意提供 `audit-depth` 与已查证证据摘要；未提供时按 deep 防御执行。
- 技能定义文件属于正式审查对象，且 skill-creator 可作为其设计规范来源。

任一假设被破坏（例如无 diff、无任何验证能力）时，技能应显式声明无法给出 Pass，而不是降级为"形式通过"。

## 4. 失效场景与删除判据

当以下条件**同时**成立时，本技能可降级为一份轻量门禁清单，甚至删除：

1. CI 门禁已完整覆盖 lint / typecheck / 测试 / 覆盖率 / SAST，且机器可读结论直接阻塞合并。
2. 模型能稳定从门禁证据推断剩余风险，不再需要结构化的 Gate 协议与分级话术。
3. 项目治理规则（单点声明、供应链边界、diff 规模阈值）已沉淀到自动化脚本或规范必查项，而非依赖审查者记忆。

降级/删除前必须确认：项目规范必查项有替代载体（脚本、测试、CI 规则），且历史 blocker 类型已被门禁覆盖。**不可推断项**（见第 5 节）在所依赖的项目规范仍存在时必须保留。

## 5. 能力替代 vs 不可推断

- **能力替代型（随模型变强应删减）**：通用"如何找 bug"的清单、SOLID 名词解释、泛化的可读性建议——这些不再是稀缺能力。
- **不可推断型（必须保留）**：diff 规模阈值、验证分级矩阵（V0–V4）与 Gate 的绑定关系、audit-depth 分级与时间盒、审计轮次上限与范围冻结、3 轮未过的改进协议、并发分区与单模块拆分规则、产物路径（`artifacts/review-gate/`）、证据模版与多轮复查基线、复发的"约束载体"要求。模型无法自行推导项目侧的这些约定。

## 6. 项目覆盖锚点

项目可变参数，技能只保留默认值：

| 参数 | 默认值 | 项目覆盖位置 |
| :--- | :--- | :--- |
| diff 规模阈值 | 10 文件 / 800 行新增 | 项目 `AGENTS.md` |
| 最低验证矩阵 | 见 `SKILL.md` 表格 | 项目 `AGENTS.md` |
| audit-depth 分级与时间盒 | quick/standard/deep | 项目 `AGENTS.md` 或它链接的 `docs/standards/*` |
| 证据产物目录 | `artifacts/review-gate/` | 项目 `AGENTS.md` |

优先级：**技能默认 < 项目覆盖 < 会话覆盖**。项目规范与技能冲突时以项目规范为准；技能不双写项目规范，只保留一行锚点。

## 7. 关键取舍

- 用单次审查的额外开销，换取更低的漏检率与更少的返工。
- 保留"deep 防御执行"这一保守默认，代价是未声明档位时审查偏慢；这是有意为之，避免漏检。
- 不适用于无 diff、无验收标准的纯探索型任务——此时应先建立审查范围，而不是勉强出结论。
