# 通用开发规范参考（Full Stack Master）

> 本文件是相对通用的开发协作规范参考，供 Full Stack Master 编排时使用。**项目可根据自身需要在 AGENTS.md 或项目规范文档中调整**；项目内已有权威规范时，以项目规范为准（规范单点声明原则：不重复抄写，一行链接引用）。

## 1. 验证分级矩阵

验证分级矩阵（V0–V4 + RG）与"不同改动类型的最低验证要求"以 [code-reviewer](../code-reviewer/SKILL.md) 的"验证分级矩阵"为**唯一权威定义**，本文件不重复抄写。

编排时只需记住两条：

- 验证矩阵决定**最低证据门槛**，缺失即 `Reject`；audit-depth 决定**核验投入**，二者正交。
- 没有 RG（Review Gate）结论的变更只能视为"进行中"，不能视为已完成。

## 2. 分级审计协议（audit-depth）

audit-depth 分级、适用改动、时间盒，以及审计轮次与范围冻结、3 轮未过的改进协议、并发分区与单模块拆分，均以 [code-reviewer](../code-reviewer/SKILL.md) 为**唯一权威定义**，本文件不重复抄写。

编排时的调用要点：

- 调用方发起审计时显式声明 `audit-depth`（+ 理由）、变更文件清单、已验证证据摘要、本轮轮次与范围。
- 未声明 audit-depth 时按 code-reviewer 的防御默认执行。
- 审计方不自报时长；时间盒由调用方宿主时钟事后实测回填，超时仅作分级校准。

## 3. 质量门基线

- 代码变更：lint + typecheck 是基线检查，不应跳过。
- build / test 按改动影响按需执行：影响打包、入口、导出、产物或运行时启动时必须 build；影响可执行逻辑、契约或现有测试路径时必须 test。
- 如果相关检查没有运行，最终交付说明中必须明确解释原因。

## 4. 提交规范

- 提交消息遵循 Conventional Commits：`<type>(<scope>): <description>`，使用中文或用户使用的语言。
- 一个提交对应一个逻辑变更，避免"大杂烩"提交。
- 超过任务粒度约束（阈值以 code-reviewer 为唯一权威）的改动先拆分再分批提交。
- 提交必须通过 husky 钩子（commitlint / lint-staged），禁止 `--no-verify` 跳过。
- 不自动 push，推送仅限用户明确要求时执行。

## 5. 修复工作流

- **根因分析优先**：默认根因分析推理模式；先编最小复现测试（一次一个假设），不跑全量测试验证错误方向。
- **CI 作为最终裁决**：修复的验收标准是 CI 流水线全部通过，不是本地测试通过。
- CI 失败后不得回退到全量重试，应分析具体失败点针对性修复；修复一个失败点后，必须让该 job 此前被短路跳过的全部后续步骤真正执行。
- 同一问题修复失败 ≥ 2 次触发搜索优先流程；≥ 3 次停止并请求人类介入。

## 6. 安全检查要点

- 敏感文件保护：严禁修改或删除 `.env`、`AGENTS.md` 等核心配置文件。
- 密钥脱敏：绝不在代码或日志中硬编码密钥、Token。
- 供应链信任：新增依赖 / MCP / 外部 skill 时验证来源（官方 registry、typosquatting 拼写、钉版本锁文件）。
- 删除操作前验证路径存在且非空，禁止批量删除（`rm -rf` / `Remove-Item -Recurse` 等）。
