# Security Guardian

铁律：把“没有看到明显校验”视为真实风险，直到证据证明它是安全的。

> 项目覆盖：若存在 `.ai/overrides/skills/security-guardian.md`，先加载并按其规则执行；冲突时以覆盖文件为准（优先级：会话 > 项目覆盖 > 核心默认）。

## 两类任务路由

两类任务都进本技能，但流程不同：

- **A. 审计正在写 / 正在改的代码**（鉴权、权限、输入处理、写入、密钥、日志、外部调用）→ 走下面「工作流」的 Step 1–3。
- **B. 给定一条已发布的运行时 / 依赖公告，判定自家项目与线上站点是否命中**（「这个洞影响我吗」）→ 走 `references/runtime-cve-impact-check.md` 的五步法，**不能用泛代码审计代替**：它靠真实版本与真实可达路径，而不是看代码写了什么。

不适用：批量处理 GitHub 告警（Dependabot / Code Scanning）→ 用 dependfix 的 `dependfix-remediator`（本仓库不再单独维护该技能）；持续监控与分层通知属运维侧动作，不在本技能。

B 类的两把尺（其余判据见 reference）：版本以**线上实际**为准（声明 `engines` ≠ lockfile ≠ 镜像 / 容器内 `-v`，拿不到就写「需核对部署版本」）；**区间查不到 ≠ 安全**（改看落后度），命中 CISA KEV 则优先于任何 CVSS 分数。

## 工作流

- [ ] Step 1: 标记敏感面 ⚠️ REQUIRED
	- [ ] 1.1 识别登录、会话、权限、数据写入、文件访问、外部请求和 secrets。
	- [ ] 1.2 标记涉及用户身份、租户边界和高价值数据的路径。
- [ ] Step 2: 逐类审计 ⚠️ REQUIRED
	- [ ] 2.1 查鉴权与授权是否完整。
	- [ ] 2.2 查输入处理是否存在注入、XSS、路径遍历或命令执行风险。
	- [ ] 2.3 查日志、配置和提交内容是否泄露 secrets。
	- [ ] 2.4 查依赖与默认配置是否存在危险默认值。
- [ ] Step 3: 评估影响
	- [ ] 3.1 明确可利用性、影响范围和修复优先级。
	- [ ] 3.2 不确定时说明需要人工核验的点，而不是轻率放行。

## 反模式

- 只扫 secrets，不审权限与输入处理。
- 看到 helper 名字像 requireAuth 就默认安全。
- 把“本地环境”“内部系统”当成可接受的安全豁免。

## 交付前检查

- [ ] 已覆盖鉴权、授权、输入、日志、配置和依赖几个维度。
- [ ] 每个高风险点都说明了利用方式或影响。
- [ ] 不确定的点已明确标注人工核验需求。
- [ ] 没有以环境或规模为理由弱化安全结论。
- [ ] B 类任务已按「确证命中 / 待核 / 未命中」三档给出结论，并附可复现命令。
