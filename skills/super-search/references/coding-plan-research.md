# AI Coding Plan / 订阅套餐定价与性价比调研工作流

用于深度调研一个 AI 编程订阅套餐（Coding Plan）的定价、额度、模型包含、使用限制以及竞品对比。适合 `depth=normal` 模式。

---

## 与 AI 模型调研的区别

| 维度 | AI 模型调研 | Coding Plan 调研 |
|:-----|:-----------|:----------------|
| **核心问题** | 模型能力、技术架构、benchmark | 价格、额度、模型覆盖、限制条件 |
| **关键信源** | 官方博客、arXiv 论文、HuggingFace | **官方定价页、社区对比页（CodingPlan.org）、Reddit 投诉帖** |
| **数据敏感点** | Benchmark 分数、参数量 | **价格区域差异（US vs CNY）、额度倍率、隐藏限流** |
| **对抗搜索重点** | 社区对模型能力的质疑 | **服务限流/429 投诉、涨价史、额度未兑现** |
| **主要输出** | 模型能力定位、使用推荐 | 套餐横向对比表、性价比评级、避坑提醒 |

## 关键分析维度

### 1. 套餐定价（需要多源确认）

| 维度 | 说明 |
|:-----|:------|
| **月费（美元）** | 官方定价，注意有会海内外差异 |
| **月费（人民币）** | 国内版价格，通常按¥8左右汇率兑换但可能不同 |
| **年费折扣** | 年付通常有折扣，但**不推荐年付**（政策变动风险大）|
| **首月优惠** | 很多套餐有首月折扣或免费试用 |

### 2. 额度体系（核心！）

| 维度 | 说明 |
|:-----|:------|
| **额度单位** | prompts次数 / token量 / 美元价值 / **Credits积分**（四种不同计费方式） |
| **滚动窗口** | 5小时滚动窗口 vs 固定时间段重置 vs **月度总量（无5h限制）** |
| **倍率消耗** | 部分平台不同模型消耗额度倍数不同（如GLM-5.1高峰期3-4x、MiMo-Pro输出token消耗600 Credits/个）|
| **周/月上限** | 是否有周限额或月总额度 |
| **高峰期差异** | 部分套餐（如GLM）高峰期消耗倍数更高（2x-3x） |
| **额度耗尽行为** | 停机（MiMo） vs 自动转按量（Copilot） vs 降速 |
| **并发限制** | 同时可用终端数是否受限 |

### 3. 额度倍率（性价比关键指标）

**公式**：额度倍率 = 当前周期额度价值 ÷ 月费价格

| 倍率 | 含义 | 例子 |
|:----:|:-----|:-----|
| <1 | 性价比差，月费超过实际获得价值 | GLM Lite 0.24 |
| 1-5 | 一般 | GLM Pro ~3.9 |
| 5-10 | 较好 | OpenCode Go ~6x, Ollama Pro ~10x |
| 10+ | 极好 | MiniMax Plus ~22x |

> ⚠️ 额度倍率是一个相对指标，前提是认可该模型的单位定价。高倍率不一定代表总价值更高。

### 倍率计算工作示例（以 GLM Pro ¥149 / MiMo Standard ¥99 / MiniMax Plus ¥49 为例）

**步骤 1：获取月度 Token 总额度**

| 套餐 | 月费 | 月 Token 额度 | 数据来源 |
|------|------|-------------|---------|
| GLM Pro (GLM-4.7) | ¥149 | ~6.4亿 | awesome-coding-plan 实测（不含5.2倍数消耗）|
| MiMo Standard (V2.5) | ¥99 | ~8.66亿 | 官方 Credit ÷ 加权均耗(12.7cr/token) |
| MiniMax Plus (M2.7) | ¥49 | ~6亿 | 官方标称（月度 ~6亿+ token M3 用量） |

> **关键陷阱**：各平台额度单位不同（tokens / Credits / 请求次数），不能直接比。必须统一转换为同一单位（建议 tokens）后再对比。

**步骤 2：计算加权平均 API 单价**

Agent 场景下使用 90% 缓存命中率、99.5% input、0.5% output 的推算：

| 模型 | Input (缓存) ¥/M | Input (未缓存) ¥/M | Output ¥/M | 加权均价 ¥/M |
|------|:-:|:-:|:-:|:-:|
| GLM-4.7 | 0.6 | 3 | 12 | ~2.69 |
| MiMo-V2.5 | 0.02 | 1 | 2 | ~0.57 |
| MiniMax M2.7 | 0.42 | 2.1 | 8.4 | ~2.53 |

**步骤 3：计算额度价值**

```
GLM Pro:     6.4亿 tokens × ¥2.69/M = ¥1,721
MiMo Standard: 8.66亿 tokens × ¥0.57/M = ¥494
MiniMax Plus: 6亿 tokens × ¥2.53/M = ¥1,518
```

**步骤 4：计算倍率**

```
GLM Pro:     ¥1,721 ÷ ¥149 = 11.6×
MiMo Standard: ¥494 ÷ ¥99 = 5.0×
MiniMax Plus: ¥1,518 ÷ ¥49 = 31.0×
```

> **倍率解读**：MiniMax 倍率最高，因为官方 Token 额度标称巨大且有请求次数限制（1500次/5h），实际未必用得到。MiMo 倍率看似最低，但其无 5h 窗口限制 + 夜间 0.8× 消耗，实际可用比例更高。倍率≠实际体验，必须结合窗口限制、高峰期差异、限流情况综合判断。

### 单位归一化速查

| 原始单位 | 转换到 Token | 注意事项 |
|----------|------------|---------|
| **请求次数**（次/5h） | 每次请求约 3-5万 tokens（编码Agent场景） | 一次Prompt=15~20次模型调用，每次调用的 input 呈累积增长 |
| **Credits**（MiMo体系） | 按模型查询消耗比率 | V2.5-Pro: ~35cr/token, V2.5: ~12.7cr/token（90%缓存命中）|
| **元/月**（按量估算） | 月费 ÷ 加权均价 | 需要知道该平台各模型的 API 单价 |
| **官方标注 token 数** | 直接使用，但注意是否包含全模态 | MiniMax 的 M3 用量与图像/语音/音乐共享额度，实际文本可用 < 标称 |

### 4. 模型覆盖

| 维度 | 说明 |
|:-----|:------|
| **模型数量** | 独家模型 vs 多厂商模型聚合 |
| **模型能力** | SWE-bench/其他基准分数 |
| **是否含闭源旗舰** | 是否包含 Claude Opus、GPT-5.5 等 |
| **场景限制** | 是否只能在特定工具中使用 API Key |

### 5. 服务品质

| 维度 | 说明 |
|:-----|:------|
| **限流/429情况** | Reddit 等社区的真实体验 |
| **速度/延迟** | 用户反馈的 TPS（每秒 token 数） |
| **算力充裕度** | 高峰期是否频繁 429 |
| **涨价历史** | 是否曾突然涨价/降额度 |

## 数据交叉验证要点

| 数据类别 | 验证方法 |
|---------|:---------|
| **官方定价** | 官方页 + 至少 1 个第三方对比站确认 |
| **额度限制** | 官方文档为主，awesome-coding-plan 实测值为辅 |
| **额度倍率** | 由 awesome-coding-plan 作者计算，可引用的量化指标 |
| **社区投诉** | 需要多个独立用户的一致投诉才可采信 |
| **区域价格** | US 版和国内版 CNY 通常不同，必须分开标注 |
| **涨价历史** | 社区帖子 + 什么值得买/类似平台交叉确认 |

### 处理矛盾的原则

1. 定价矛盾 → 以**官方定价页**为准（页面截图或爬取内容）
2. 额度矛盾 → 以官方文档白纸黑字为准，社区实测作为参考
3. 服务稳定性矛盾 → 以**多个独立用户的共识**为准。有人快有人慢是正常的；所有人都说慢才可信
4. API Key 场景限制矛盾 → 以 **官方文档**为准，不要采信第三方文章中过时的信息

## 报告格式要点

### 表格设计原则

1. **维度对齐**：所有对比套餐使用相同维度列（价格、模型数、5h额度、额度倍率、场景限制）
2. **价格带分组**：按 `$0-5 / $10 / $15-20 / $100+` 分层呈现
3. **高亮最佳值**：在对比表中用 **加粗** 标记每个维度的最佳值
4. **标注来源**：所有定价单元格标注来源编号

### 关键锚点指标

| 指标 | 解释 |
|:-----|:------|
| **额度倍率** | 你付的钱能买到多少"额度价值"，越高越划算 |
| **5小时限额** | 滚动窗口内的使用上限，决定爆发式使用的可行性 |
| **模型覆盖** | 能用的模型数量和质量 |
| **服务稳定性** | 是否频繁限流/429 |

### ⚠️ 警告标注模板

```
> ⚠️ **{品牌} 高峰期（{时间}）消耗 {N}x 配额**：这意味着高峰期实际可用额度仅为标称的 1/{N}。
> ⚠️ **社区广泛反馈限流/429 问题**：参见 [来源](link)。
> ⚠️ **涨价历史**：202X年X月曾涨价 ≥{N}%，同时额度降低 {N}%。
```

### 定价锚点基准（DeepSeek 原则）

调研 Coding Plan 的性价比时，始终以 **DeepSeek-V4-Flash 的 API 按量定价**作为价格基准线和参照锚点：

| 模型 | 输入(缓存) ¥/M | 输入(未缓存) ¥/M | 输出 ¥/M | 加权均价(90%缓存) |
|------|:-:|:-:|:-:|:-:|
| **DeepSeek-V4-Flash** 🥇 | 0.02 | 1 | 2 | **~0.57** |
| DeepSeek-V4-Pro (2.5折) | 0.025 | 3 | 6 | ~1.71 |

DeepSeek-V4-Flash 按量付费的加权均价仅 **¥0.57/百万 token**。这意味着：¥100 在 DeepSeek 上可跑约 **1.75亿 tokens**，远超多数订阅套餐的实际可用额度。

**在评估 Coding Plan 性价比时，始终问：**
1. 这个套餐月费¥X，折合能买多少 DeepSeek 按量 tokens？
2. 套餐的旗舰模型是否值得付出（定价倍率 vs 能力差距）？
3. 如果用量超过套餐限制，溢出部分有何代价？

> ⚠️ 此原则不适用于多模态场景（DeepSeek 不支持图像/语音/视频），也不适用于对模型代码能力有极高要求的场景。

### 五维评分框架

当需要对多个平台做综合对比时，使用以下 5 个维度量化评分（每项 1-10 分）：

| 维度 | 说明 | 评估方法 |
|------|------|---------|
| **模型能力** | 旗舰/顶级模型的代码能力 | SWE-bench Pro/Verified 分数 + 社区实测反馈 |
| **性价比** | 月额度价值 ÷ 月费倍率 | 按倍率计算工作示例的 4 步法 |
| **额度充裕度** | 是否够用、窗口限制严不严 | 5h 窗口限制、高峰期倍数消耗、限流情况 |
| **稳定性** | 限流/429/速度一致性 | 社区投诉频率、高峰期速度实测 |
| **生态兼容性** | 接入难度/工具限制 | 是否限制非官方工具、兼容 OpenClaw/Hermes 等 |

**评分后综合展示**：

```
| 维度 | 平台A | 平台B | 平台C |
|------|:----:|:----:|:----:|
| 模型能力 | 8.5 | 8.0 | 7.5 |
| 性价比 | 6.0 | 8.5 | 9.0 |
| 额度充裕度 | 4.0 | 9.5 | 6.0 |
| 稳定性 | 3.0 | 8.0 | 8.0 |
| 生态兼容性 | 5.0 | 8.5 | 9.0 |
| **综合** | 5.3 | 8.5 | 7.9 |
```

以 DeepSeek 为基准的 "值不值" 快速判断：

```
月费¥X → 折算 DeepSeek 按量可用 N 亿 tokens
是否旗舰模型？→ 是：可能值（当模型能力差距可接受）
               → 否：应考虑直接用 DeepSeek 按量
是否有特殊价值？→ 无窗口限制/全模态/独家模型 → 可溢价
```

## 额度消耗测算（官方数据反推单次请求成本）

当官方文档给出「每 5 小时/每周/每月请求数」和「典型请求模式（每次请求的输入/缓存/输出 token 数）」时，可以精确反推额度使用情况，评估"什么任务能烧完额度"：

**公式**：单次请求成本 = 输入 token × 输入单价 + 缓存 token × 缓存读取单价 + 输出 token × 输出单价

**验证技巧**：用计算出的单次成本 × 官方请求数，应约等于官方美元额度（如 79,050 请求 × $0.000379 ≈ $30）——能对上说明定价模型正确。

**场景模拟法**（回答"什么任务能 7 天内用完 $X"）：

| 场景 | 估算方法 |
|------|---------|
| 日常交互式开发 | 每小时 ~60 次请求 × 每天几小时 → 通常只消耗额度的 1-2% |
| 多 agent 并行 | 子代理数 × 每会话请求数 × 每日批次 |
| 无头 API 批量处理 | 每分钟请求数 × 60 × 24 |
| 大规模重构/审查 | 文件数 × 每文件请求数（审查 ~3-5，重构 ~20） |

**关键洞察**：
- 缓存读取往往是成本大头（DeepSeek Flash 单次 $0.000379 中缓存占 $0.000190 ≈ 50%）——长上下文多轮会话烧额度更快
- 日常人工开发几乎不可能用完额度（差 10-50 倍）；只有批量/并行/自动化场景能触顶
- 注意 5 小时滚动窗口限制（爆发式使用先触发它，而非周/月总额）

## 中国区 Coding Plan 常见销售模式

国内 AI 编程套餐市场已进入 "价格战→涨价收割" 周期，调研时需要特别关注以下模式：

| 模式 | 说明 | 案例 |
|:----|:-----|:-----|
| **首月优惠** | 首月极低价格吸引新用户（¥7.9-¥49.9），续费恢复原价 | 火山方舟首月¥9.9/¥49.9 |
| **限量抢购** | 每天指定时段（如10:30）限量开放购买，非随时可买 | 火山方舟、智谱GLM |
| **倍率消耗** | 不同模型/时段消耗额度倍数不同（1x-4x），实际可用额度远低于标称 | GLM-5.1 高峰期3x-4x；火山方舟倍率消耗 |
| **区域价格差** | 同一厂商国内定价通常远低于海外（国内价≈海外价1/3-1/2） | 智谱GLM Lite: 国内¥49 vs 海外$18(≈¥144) |
| **Credits 积分制** | 按月给固定 Credits, 不同模型/操作消耗不同, 用完停机 | 小米MiMo Token Plan |
| **无5h窗口** | 按月总量计，无每5小时滚动限制，适合高强度连续使用 | 小米MiMo Token Plan |
| **聚合平台** | 一个套餐可调用多家模型，主家模型算力更充足 | 火山方舟、阿里百炼 |
| **停售升档** | 低价档位逐步停售，迫使用户转向更高价档位 | 阿里百炼Lite停售(2026.4) |
| **场景限制** | 套餐仅限Coding/编程工具使用，禁止API直接调用 | 小米MiMo、GLM、阿里百炼 |
| **涨价周期** | 先低价获客→用户习惯后涨价，通常6-12个月一轮 | 智谱GLM 2026.2涨价≥30% |
| **模型下线/迁移** | 旧版模型到期下线，用户需主动迁移至新版，信用额度算法可能变化 | MiMo V2→V2.5 系列迁移(2026.6.30) |

## 套餐动态监控方法论

需要持续监控的事件类型：

| 事件类型 | 检测方法 | 示例 |
|---------|---------|------|
| 新模型发布 | 搜索 `{provider} 新模型`、`{provider} blog release` | Kimi K3 2026-07-16 |
| 套餐价格调整 | 官方定价页 + 社区讨论 | 智谱 GLM 2026-02 涨价 ≥30% |
| **售罄/暂停新订阅** | 官方会员页状态 + 新闻报道 | Kimi K3 发布后 48 小时所有套餐售罄（2026-07-20）|
| 套餐结构调整 | 官方公告 + 版本更新日志 | 阿里百炼 Lite 停售 |
| **模型下线/迁移** | 官方通知 + 社区提醒 | MiMo V2→V2.5 迁移截止 2026-06-30 |

### 检测方式

| 方式 | 适用场景 | 说明 |
|------|---------|------|
| 官方定价页直连 | 获取最新官方定价 | 优先使用，注意 SPA 页面可能需要浏览器 |
| 搜索关键词监控 | 价格变更/套餐调整 | 如「Kimi K3 套餐调整」「DeepSeek 降价」 |
| 论坛/Reddit 社区 | 用户反馈验证 | r/opencodeCLI、forum.moonshot.ai |
| 官方公告/Changelog | 确认变更原因和时间 | kimi.com/help/kimi-blackboard/ |

### 快速响应清单

当发现新模型发布时，调研以下内容并在 24 小时内完成：

1. **定价对比** — vs 同梯队竞品（API 单价 + 套餐月费）
2. **配额换算** — 套餐额度能支撑多少实际使用
3. **能力定位** — 在 Intelligence Index / SWE-bench 上的位置
4. **可用性检查** — 是否立即可用（API? 套餐? 售罄?）
5. **竞品反应** — 其他厂商是否跟进了降价/调整

### 常见陷阱

- ❌ 忽略缓存折扣 — Kimi K3 标价 $15/百万输出看起来很贵，但 90%+ 代码缓存命中率下有效输入成本仅 $0.30
- ❌ 只看价格不看配额 — Kimi K3 月配额 490 次 vs Flash 158,150 次（322 倍差距），只看每 token 价格会误判
- ❌ 忽略推理 tokens 计费 — 部分模型（如 K3）始终推理，推理 tokens 按输出计费，简单查询也烧钱
- ❌ 认为同一厂商不同套餐共用额度池 — Kimi 会员的聊天和编码共享额度
- ❌ 忽略时间窗口限制 —「每5小时」周期在实际高强度使用中比「每月总额」更先被触发
- ✅ 核心原则：**不考虑使用场景的性价比分析没有意义**。主力模型用便宜的，复杂任务切贵的

## 常见坑

- ❌ 只搜索官方定价页而不检查社区真实反馈（限流问题常被官方隐瞒）
- ❌ 把 US 定价和国内 CNY 定价混为一谈（不同版本可能定价和额度不同）
- ❌ 忽略高峰期差异（如 GLM 14-18 点 3x 消耗）
- ❌ 只比较月费不比较"额度倍率"（$3 但只能调用 80 次/5h ≠ 划算）
- ❌ 不关注涨价历史（AI 套餐行业普遍是"先低价获客，再涨价收割"）
- ❌ 只搜正面评价不做对抗性搜索（看 Reddit 最差评论比好评更有价值）
- ❌ 忽略额度计算方式差异（prompts 次 vs token 量 vs 美元价值，不可直接比较）
- ❌ 将第三方转载的价格表当作一手数据（转载可能导致信息过时）
