# 提案接收与反馈（proposals）

> 本文件规定项目如何接收上游提案、如何把结论回传，以及上游如何例行扫描下游。提案本身见 `docs/proposals/`。

## 1 接收时机

- **默认在阶段结束或下一阶段开始前**处理提案；如项目选择临时插入，按 §2 的权限处理。
- 进入新阶段、评估下一阶段任务或整理 backlog 时，先检查是否有新提案。
- 处理前提：工作区干净（`git status --porcelain` 为空）。「干净」与「进行中任务」的判定沿用 [task-start.md](./task-start.md)；阶段收尾遇到未提交改动时，先完成收尾提交再处理提案。

## 2 处理方式

项目可自行选择：

- 作为**临时插入任务**立即处理：一般提案由项目工作流决定，**关键提案需用户裁决**；
- 进入 **backlog** 等待评估；
- 按项目自身工作流处理。

无论哪种，都必须给出状态，不得静默忽略：

| 状态 | 含义 | 要求 |
| :--- | :--- | :--- |
| 待研判 | 已收到，尚未评估 | 记录在项目待办或 issue |
| 已采纳 | 决定实施 | 写明范围与验收；状态留在项目 backlog / issue |
| 延后 | 进 backlog | 写明触发条件或目标阶段 |
| 不采纳 | `optOut` | 写明理由（不适用 / 成本高于收益 / 已有等价实现） |

> 台账只记录「不采纳」（`optOut`）与「已验证样板」（`mature`）；待研判 / 已采纳 / 延后属于项目侧状态，不写进 registry，避免与项目 backlog 双写。

**关键提案**（安全、发布阻塞、跨项目能力）应由用户裁决是否优先处理，不由 agent 自行插队。

## 3 下游 → 上游反馈

按以下顺序选择：

1. **本地有 `cmyr-skills-agents` 且用户授权**：直接修改上游仓库（按上游的提交与审查规范），不要在下游 fork 中长期保留通用改进。
2. **否则提交 GitHub issue**：仓库为 `CaoMeiYouRen/cmyr-skills-agents`；写清能力名、现状与痛点、建议改动、影响项目、验收标准。

经用户授权的紧急本地改动可以先行，但必须同时提 issue，且仅限紧急例外、不得作为常规路径；上游合入后收敛回核心。

## 4 上游例行扫描

- **时机**：至少满足以下之一——每个提案批次前、每月一次、下游发布节点之后。
- **动作**：
  1. 跑 `node scripts/check-capabilities.mjs --projects <下游路径...>`，得到能力矩阵；
  2. 对比各项目 `AGENTS.md`、`docs/standards`、`.github/workflows` 的新增能力与做法；
  3. 把「已有项目验证、其他项目缺失」的能力登记为 `candidate`，再决定是否形成提案；
  4. 已收敛的能力只做漂移检测，不重复提案。
- **输出**：更新 `capabilities/registry.json` 与 `docs/proposals/`；**不直接修改下游**。

## 5 验收

- [ ] 阶段结束或下阶段开始前有「提案检查」记录（有/无、处理方式）。
- [ ] 不采纳的提案有 `optOut` 理由。
- [ ] 不采纳的提案有 `optOut` 理由；已采纳 / 延后的状态在项目 backlog / issue 可查；达到样板标准时再更新 `mature`。
- [ ] 上游扫描有矩阵输出，且没有把已收敛能力重复提案。
